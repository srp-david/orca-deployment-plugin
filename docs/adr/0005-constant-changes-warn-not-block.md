# 상수 값이 바뀐 class 는 경고만 하고 막지 않는다

Java 는 컴파일 시간 상수(`final` 기본형·문자열)를 쓰는 쪽 class 에 값을 복사해 넣는다. 그래서 상수 값을 바꾼 class 만 올리면, 그 상수를 쓰는 다른 class 는 운영에서 옛 값으로 계속 돈다. 반영 목록은 PR 에서 바뀐 소스로 만들기 때문에 이 "쓰는 class" 는 목록에 들어가지 않는다.

plan 은 운영 class 와 새 class 의 상수를 비교하고, 값이 바뀐(또는 상수가 아니게 된) 상수의 이름이 낱말로 나오는 다른 `.java` 가 반영 목록에 없으면 **경고**로 그 파일들을 보여 준다. 경고는 run 을 막지 않고, 올릴지는 사람이 판단한다.

막지 않는 이유:

- 쓰는 곳 찾기가 낱말 검색이다. 같은 이름의 다른 상수·지역 변수·주석도 잡히므로, 막으면 상관없는 반영이 멈춘다. class 이름이나 상속 관계로 걸러 내면 반대로 놓치는 길이 생긴다(`식.LIMIT`, 상속받은 이름, `import static`).
- 실제로 드물다. 이 도구를 쓰는 저장소의 이력(커밋 150개)에서 이미 있던 공개 상수의 값을 바꾼 커밋은 없었다.
- IntelliJ 로 올릴 때도 이 판단은 사람이 했다. 도구가 할 일은 놓치지 않게 보여 주는 것까지다.

## Considered Options

- **문제로 막기**: 처음 만든 방식. 낱말만 같은 경우에도 그 PR 을 도구로 반영할 길이 없어진다.
- **경고 + 사람이 "확인함" 해야 업로드**: 확인 기록을 run 에 남기는 방식으로 만들었다가 뺐다. 확인이 어떤 경고·어떤 반영 목록에 대한 것인지 묶고, 경고 파일이 지워지거나 바뀐 경우와 동시 실행까지 다뤄야 해서, 드문 경우에 비해 장치가 커진다.
- **검사를 빼기**: 가장 단순하지만 상수가 바뀌어도 아무 표시가 없다. 검사는 plan 이 원래 받는 운영 class 를 그대로 쓰므로 남겨 두는 비용이 거의 없다.
- **직전 커밋과 반영 커밋을 각각 빌드해 비교**: 실제로 바뀐 class 를 정확히 고를 수 있어 이 경고가 필요 없어진다. 빌드 전용 체크아웃, 빌드 시간, 운영 class 와 바이트가 같게 빌드되는지 확인이 먼저 필요해 미뤘다.

## Consequences

- 경고를 읽지 않고 올리면 쓰는 class 가 빠질 수 있다. 패널은 경고를 반영 목록 카드 위쪽에 노란 안내로 보여 주고, 스킬은 경고를 빼놓지 않고 보여 주되 대신 판단하지 않게 했다.
- 이름을 `\uXXXX` 로 적은 소스, 예전 반영에서 이미 빠진 class, 운영에 없던 새 class 는 이 검사로 찾지 못한다.
- class 의 나머지 내용은 여전히 plan 때 운영본과 대조하지 않는다(직전 커밋의 class 가 없음). 운영에서 직접 고친 class 는 백업으로만 되돌릴 수 있다.
