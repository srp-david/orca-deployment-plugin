# 오래된 백업은 run 기록을 남기고 백업 파일만 지운다

run 마다 덮어쓰기 전 운영 파일이 `backup/` 에 쌓인다(올릴 파일의 고정본 `stage/` 는 업로드가 끝나면 이미 지운다). 지금은 일주일에 1MB 도 안 되지만 끝없이 쌓이므로 **백업 정리**를 둔다: 90일 지난 run 의 `backup/` 만 지우고 run 폴더와 그 안의 기록(`plan.tsv`, 상태 표시, 로그)은 남긴다. 되돌리기의 나중 run 판정과 PR 목록의 "반영됨" 표시가 이 기록을 보기 때문이다(ADR 0004). 백업을 지운 run 은 상태는 그대로 두고 **백업 지움** 표시를 붙이며, 되돌리기와 (올리지 않은 run 이면) 업로드를 막는다.

규칙:

- 나이는 올린 run 이면 업로드를 시작한 시각, 올리지 않은 run 이면 백업을 받은 시각으로 잰다. 업로드 시각을 모르는 bash 시절 run 은 넣지 않는다.
- 숨긴 run 도 넣는다. 부분 업로드 run 은 넣지 않는다(되돌려야 하는 상태).
- 어느 운영 파일이든 그 파일을 마지막으로 올린 run 은 90일이 지나도 백업 전체를 남긴다. 그 백업이 그 변경 전 운영본의 유일한 사본일 수 있다(운영에서 손으로 고친 파일은 git 에도 없다). "나중에 올림"은 모든 줄을 끝까지 올린 run(업로드됨·대조됨, 되돌리지 않은 것)만 친다. 부분 업로드 run 은 어느 줄이 실제로 올라갔는지 믿을 수 없고 곧 되돌릴 상태라, 앞 run 의 보호를 풀지 않는다(부분 업로드 run 과 그 직전 백업이 함께 남는다). "나중에 올림"은 같은 대상의 run 만 본다(되돌리기의 나중 run 판정과 같은 범위). 같은 호스트·포트·경로라도 대상이 다르면 FTP 계정마다 루트(chroot)가 달라 다른 파일일 수 있고, 다른 대상의 업로드·되돌리기는 이 대상의 잠금 밖에서 돌기 때문이다.
- 업로드한 흔적(`upload.started`·`upload.done`·로그의 업로드 시작)이 있는데 `plan.tsv` 가 없거나, 비었거나, 줄이 깨졌으면 무엇을 올렸는지 알 수 없으므로 백업을 남기고 그 이유를 목록에 보인다. 그런 run 은 다른 run 의 보호를 푸는 "나중에 올림"으로도 치지 않는다.
- 지우기 전에 run 폴더와 지울 폴더(`backup`, `backup.tmp`)가 링크·정션이 아니고 실경로가 그 대상의 run 기록 폴더 안인지 본다. 아니면 지우지 않고 이유를 목록에 보인다. 크기를 셀 때도 링크를 따라가지 않는다.
- 지우기 전에 `backup.pruning`(지우는 중)을 남기고, 다 지운 뒤 `backup.pruned`(지움)로 바꾼다. 지우는 중으로 남은 run 도 백업 지움처럼 되돌리기·업로드·다시 백업을 막는다. 한 run 을 지우다 실패해도 나머지 run 은 계속 지우고, 실패(오류와 경로)를 결과와 그 run 의 로그에 남긴다(CLI 는 0 아닌 종료). 지우는 중으로 남은 run 도 다음 정리에서 지금의 보존 규칙(나이, 부분 업로드, plan.tsv, 마지막 run, 링크)을 다시 거친다. 지울 수 있으면 목록에 다시 나와 남은 백업을 마저 지우고, 규칙에 걸리면(예: 나중 run 을 되돌려 다시 마지막 run 이 됨) 이유와 함께 남기며 지우는 중 표시는 그대로 둔다(남은 백업이 온전한지 알 수 없어 되돌리기·업로드는 계속 막는다).
- 사람이 run 기록 화면의 버튼으로 지울 목록과 크기를 보고 확인해야 지운다. CLI `prune --target <대상>` 은 목록과 그 목록의 확인 코드만 보이고, `prune --target <대상> --plan <코드> --yes` 가 지운다. 잠금 안에서 다시 판단한 목록의 코드가 다르면 아무것도 지우지 않는다(업로드·되돌리기의 확인 코드와 같은 원칙). 패널은 사람이 본 run 이름들을 보내고 그중 지금도 지울 수 있는 것만 지운다. 에이전트가 `--yes` 로 부르면 가드 훅이 사람에게 묻는다.
- 90일은 코드에 고정한다.

## Considered Options

- **run 폴더째 지우기**: 디스크는 가장 많이 줄지만 나중 run 판정이 지운 run 을 못 봐서 앞 run 을 되돌리다 더 새 반영을 덮어쓸 수 있다(ADR 0004 에서 뺀 이유와 같다).
- **예외 없이 90일**: 규칙은 단순하지만 오래 안 고친 파일의 마지막 변경을 되돌릴 길이 없어진다. 예외로 남는 run 은 파일 수만큼도 안 된다.
- **파일 단위로 남기기**: 되돌리기는 run 전체를 되올리므로 백업이 일부만 남은 run 은 어차피 되돌릴 수 없다.
- **새 run 을 만들 때 자동으로 지우기**: 되살릴 수 없는 일을 사람이 모르게 한다. 지금 쌓이는 양으로는 자동일 이유가 없다.
- **대상 설정에 보관 일수 두기**: 대상마다 다를 이유가 아직 없다. 필요해지면 그때 뺀다.

## Consequences

- 90일 지난 run 은 (마지막 run 예외가 아니면) 되돌릴 수 없다. 그 사이 같은 파일을 다른 run 이 건드렸다면 원래도 되돌리기가 막힌다.
- 마지막 run 예외 때문에 오래 안 고친 파일을 올린 run 의 백업은 계속 남는다.
- 마지막 run 은 정리할 때의 상태로 정한다. A 의 백업을 지운 뒤에 같은 파일을 나중에 올린 B 를 되돌리면, 운영의 그 파일은 A 가 올린 것이 되지만 A 는 되돌릴 수 없다.
- 마지막 run 판정은 같은 대상의 run 만 보므로 대상 잠금 안에서 닫힌다. 같은 서버·같은 계정을 쓰는 대상이 둘이면 서로의 나중 업로드를 모르고 각자의 마지막 run 을 남긴다(더 남기는 쪽으로 틀린다).
