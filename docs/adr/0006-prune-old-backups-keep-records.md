# 오래된 백업은 run 기록을 남기고 백업 파일만 지운다

run 마다 덮어쓰기 전 운영 파일이 `backup/` 에 쌓인다(올릴 파일의 고정본 `stage/` 는 업로드가 끝나면 이미 지운다). 지금은 일주일에 1MB 도 안 되지만 끝없이 쌓이므로 **백업 정리**를 둔다: 90일 지난 run 의 `backup/` 만 지우고 run 폴더와 그 안의 기록(`plan.tsv`, 상태 표시, 로그)은 남긴다. 되돌리기의 나중 run 판정과 PR 목록의 "반영됨" 표시가 이 기록을 보기 때문이다(ADR 0004). 백업을 지운 run 은 상태는 그대로 두고 **백업 지움** 표시를 붙이며, 되돌리기와 (올리지 않은 run 이면) 업로드를 막는다.

규칙:

- 나이는 올린 run 이면 업로드를 시작한 시각, 올리지 않은 run 이면 백업을 받은 시각으로 잰다. 업로드 시각을 모르는 bash 시절 run 은 넣지 않는다.
- 숨긴 run 도 넣는다. 부분 업로드 run 은 넣지 않는다(되돌려야 하는 상태).
- 어느 운영 파일이든 그 파일을 마지막으로 올린 run 은 90일이 지나도 백업 전체를 남긴다. 그 백업이 그 변경 전 운영본의 유일한 사본일 수 있다(운영에서 손으로 고친 파일은 git 에도 없다). "나중에 올림"은 모든 줄을 끝까지 올린 run(업로드됨·대조됨, 되돌리지 않은 것)만 친다. 부분 업로드 run 은 어느 줄이 실제로 올라갔는지 믿을 수 없고 곧 되돌릴 상태라, 앞 run 의 보호를 풀지 않는다(부분 업로드 run 과 그 직전 백업이 함께 남는다). "나중에 올림"은 같은 대상의 run 만 본다(되돌리기의 나중 run 판정과 같은 범위). 같은 호스트·포트·경로라도 대상이 다르면 FTP 계정마다 루트(chroot)가 달라 다른 파일일 수 있고, 다른 대상의 업로드·되돌리기는 이 대상의 잠금 밖에서 돌기 때문이다.
- 같은 대상 안에서도 FTP 계정을 바꿀 수 있다(자격 증명 관리자나 netrc 의 사용자를 바꿈). 그래서 업로드를 시작할 때 run 폴더의 `upload.account` 에 올린 계정의 지문을 남긴다: `sha256("prod-deploy account\n" + 호스트(소문자) + ":" + 포트 + "\n" + 사용자 이름)` 앞 16자. 비밀번호는 넣지 않고 사용자 이름도 그대로 남기지 않는다. 사용자 이름은 실제로 curl 에 보낸 값을 앞뒤 공백만 빼고 글자 그대로 쓴다. netrc 도 엔진이 한 번 읽어 대상 호스트의 login·password 를 정하고, curl 에는 자격 증명 관리자와 같은 길(`-K -` stdin)로 그 값을 넘긴다(curl 이 netrc 를 따로 읽지 않는다). 그래서 지문은 늘 보낸 사용자 이름의 것이고, 업로드 도중 netrc 가 바뀌어도 그 업로드는 처음 읽은 값으로 끝까지 보낸다. 엔진은 netrc 를 엄격하게 읽는다(`src/engine/netrc.ts`): 흔한 모양(줄 머리 `#` 주석, 큰따옴표 값과 `\` 이스케이프, 항목 밖이나 다 적은 항목 뒤의 `macdef` 본문, `machine`·`default`·`login`·`password`)만 받고, 대상 호스트의 machine 항목을 쓰며 없으면 default 를 쓴다(둘 다 맞으면 machine). 대상 호스트 항목 둘, 한 항목의 login·password 두 번, 모르는 낱말(`account` 포함), 항목 안의 macdef, 닫지 않은 따옴표, 제어 문자, UTF-8 이 아닌 파일 같은 이상한 모양은 파일 어디에 있든 고르지 않고 멈춘다(줄 번호와 이유만 적고 값은 적지 않음). 대상 항목에 login 이나 password 가 없어도 멈춘다. 지문은 "업로드 시작" 표시(로그·`upload.started`)보다 먼저 쓴다: 쓰지 못하면 보내기 전에 멈추고 같은 run 을 다시 올릴 수 있다. "나중에 올림"은 지문이 같은 run 만 친다. 다른 계정의 업로드는 루트가 달라 다른 파일일 수 있으므로 앞 run 의 보호를 풀지 않는다. 되돌리기의 나중 run 판정도 같은 규칙을 쓴다. 지문이 없는 run(지문을 남기기 전 기록)은 어느 run 과도 같은 계정으로 본다(지문을 남기기 전과 똑같이 다룬다). 지문은 이 두 판정에만 쓰고, 계정이 바뀌었다고 백업·업로드·대조·되돌리기를 멈추지는 않는다.
- 업로드한 흔적(`upload.started`·`upload.done`·로그의 업로드 시작)이 있는데 `plan.tsv` 가 없거나, 비었거나, 줄이 깨졌으면 무엇을 올렸는지 알 수 없으므로 백업을 남기고 그 이유를 목록에 보인다. 그런 run 은 다른 run 의 보호를 푸는 "나중에 올림"으로도 치지 않는다.
- 링크·정션은 두 곳에서 본다. 그 run 자신의 백업을 지울지 정할 때는 run 폴더와 지울 폴더(`backup`, `backup.tmp`)가 링크·정션이 아니고 실경로가 그 대상의 run 기록 폴더 안인지 본다(`deleteProblem`). 아니면 지우지 않고 이유를 목록에 보인다. 다른 run 의 보호를 푸는 "나중에 올림"의 근거로 쓸 때는 run 폴더의 위치만 본다(`runDirProblem`): run 폴더가 링크·정션이거나 실경로가 run 기록 폴더 밖이면 그 run 의 업로드는 세지 않는다. 크기를 셀 때도 링크를 따라가지 않는다.
- 남기는 이유(마지막 run, `plan.tsv` 손상, 링크 등)는 90일이 지나 원래 정리할 수 있었던 run(나이를 모르는 업로드 run 포함)에만 목록에 보인다. 90일이 안 된 보통 run 은 나이 때문에 아예 후보가 아니므로 목록에서 뺀다(백업은 그대로 남는다). 다만 지우다 멈춘 run 은 다시 판단해 남길 때 나이 때문이어도 그 이유를 보인다(예: "지우다 멈춘 run — 90일이 지나지 않아 남김, 백업이 일부 지워졌을 수 있음"). 지우는 중 표시가 남아 되돌리기·업로드가 막힌 까닭을 사람이 알 수 있게.
- 지우기 전에 `backup.pruning`(지우는 중)을 남기고, 다 지운 뒤 `backup.pruned`(지움)로 바꾼다(`backup.pruned` 가 있으면 `backup.pruning` 이 남아 있어도 다 지운 것으로 본다). 지우는 중으로 남은 run 도 백업 지움처럼 되돌리기·업로드·다시 백업을 막는다. 한 run 을 지우다 실패해도 나머지 run 은 계속 지우고, 실패(오류와 경로)를 결과와 그 run 의 로그에 남긴다(CLI 는 0 아닌 종료). 지우는 중으로 남은 run 도 다음 정리에서 지금의 보존 규칙(나이, 부분 업로드, plan.tsv, 마지막 run, 링크)을 다시 거친다. 지울 수 있으면 목록에 다시 나와 남은 백업을 마저 지우고, 규칙에 걸리면(예: 나중 run 을 되돌려 다시 마지막 run 이 됨) 이유와 함께 남기며 지우는 중 표시는 그대로 둔다(남은 백업이 온전한지 알 수 없어 되돌리기·업로드는 계속 막는다).
- 사람이 run 기록 화면의 버튼으로 지울 목록과 크기를 보고 확인해야 지운다. CLI `prune --target <대상>` 은 목록과 그 목록의 확인 코드만 보이고, `prune --target <대상> --plan <코드> --yes` 가 지운다. 잠금 안에서 다시 판단한 목록의 코드가 다르면 아무것도 지우지 않는다(업로드·되돌리기의 확인 코드와 같은 원칙). 패널은 사람이 본 run 이름들을 보내고 그중 지금도 지울 수 있는 것만 지운다. 에이전트가 `--yes` 로 부르면 가드 훅이 사람에게 묻는다.
- 90일은 코드에 고정한다.

## Considered Options

- **run 폴더째 지우기**: 디스크는 가장 많이 줄지만 나중 run 판정이 지운 run 을 못 봐서 앞 run 을 되돌리다 더 새 반영을 덮어쓸 수 있다(ADR 0004 에서 뺀 이유와 같다).
- **예외 없이 90일**: 규칙은 단순하지만 오래 안 고친 파일의 마지막 변경을 되돌릴 길이 없어진다. 예외로 남는 run 은 파일 수만큼도 안 된다.
- **파일 단위로 남기기**: 되돌리기는 run 전체를 되올리므로 백업이 일부만 남은 run 은 어차피 되돌릴 수 없다.
- **새 run 을 만들 때 자동으로 지우기**: 되살릴 수 없는 일을 사람이 모르게 한다. 지금 쌓이는 양으로는 자동일 이유가 없다.
- **대상 설정에 보관 일수 두기**: 대상마다 다를 이유가 아직 없다. 필요해지면 그때 뺀다.

## Consequences

- 90일 지난 run 은 (마지막 run 예외가 아니면) 되돌릴 수 없다. 그 사이 같은 파일을 다른 run 이 건드렸다면 원래도 되돌리기가 막힌다.
- 마지막 run 예외 때문에 오래 안 고친 파일을 올린 run 의 백업은 계속 남는다.
- 마지막 run 은 정리할 때의 상태로 정한다. A 의 백업을 지운 뒤에 같은 파일을 나중에 올린 B 를 되돌리면, 운영의 그 파일은 A 가 올린 것이 되지만 A 는 되돌릴 수 없다.
- 마지막 run 판정은 같은 대상의 run 만 보므로 대상 잠금 안에서 닫힌다. 같은 서버·같은 계정을 쓰는 대상이 둘이면 서로의 나중 업로드를 모르고 각자의 마지막 run 을 남긴다(더 남기는 쪽으로 틀린다).
- 계정 지문의 한계:
  - 지문은 사용자 이름으로 만든다. 같은 사용자 이름에 서버 쪽 루트(chroot)만 바뀐 경우는 같은 계정으로 보아 잡지 못한다.
  - 지문이 없는 예전 run 은 어느 계정과도 같은 계정으로 보므로, 계정을 바꾸기 전후의 run 이 예전처럼 섞일 수 있다(정리는 덜 남기고, 되돌리기는 더 막는 쪽).
  - 계정을 바꾼 뒤 앞 run 을 되돌리면 지금 계정으로 접속한다. 이것은 막지 않는다: 그 run 을 올린 계정으로 접속해 둔 뒤 되돌린다(되돌리기 전 운영 대조가 다른 루트의 파일이면 대부분 멈추지만 보장하지 않는다).
  - 사용자 이름은 글자 그대로 견준다(앞뒤 공백만 뺀다. 대소문자를 구분한다). 대소문자를 무시하는 FTP 서버에서 같은 계정을 대소문자만 다르게 적으면 다른 계정으로 본다. 그러면 정리는 더 남기고, 되돌리기는 나중 run 을 놓칠 수 있다(되돌리기 전 운영 대조가 대부분 잡지만 보장하지 않는다).
  - netrc 는 엔진의 해석으로 접속한다. curl 이 받아들이던 netrc 라도 엔진이 멈출 수 있다(위의 이상한 모양). 그러면 netrc 를 고치거나 자격 증명 관리자로 옮긴다. 엔진이 받아들이는 모양 가운데 curl 이 다르게 읽던 것(예: default 가 맞는 machine 보다 앞에 있으면 curl 은 default 를, 엔진은 machine 을 씀)은 이전(curl 이 netrc 를 읽던 때)과 다른 항목으로 접속할 수 있다. 그 항목의 계정이 틀리면 로그인 실패로 드러나고, 맞는 다른 계정이면 그 계정으로 올리며 지문도 그 계정의 것이다.
