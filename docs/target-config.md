# 대상 설정

**대상**은 반영할 곳 하나입니다: 저장소 하나 + FTP 주소 + 운영 루트. 같은 저장소에 운영·시험 대상을 여러 개 둘 수 있습니다.

대상 설정은 각자 PC 의 `~/.prod-deploy/targets/<대상 이름>.json` 에 저장됩니다(저장소에는 올라가지 않음). 패널의 **대상 설정** 탭에서 만들고 고치며, 파일을 직접 고쳐도 됩니다. 저장할 때마다 이전 설정은 `targets/.history/` 에, 지운 설정은 `targets/.deleted/` 에 남습니다.

예시: [`examples/java-war.json`](../examples/java-war.json)

```powershell
mkdir $HOME\.prod-deploy\targets -Force
copy examples\java-war.json $HOME\.prod-deploy\targets\myapp.json
notepad $HOME\.prod-deploy\targets\myapp.json   # id 는 파일 이름과 같아야 함
```

## 항목

| 항목 | 설명 | 예 |
|---|---|---|
| `id` | 대상 이름. 영문 소문자·숫자·`_` 만(`-` 는 안 됨). **만든 뒤에는 바꿀 수 없습니다**(run 기록이 이름에 묶임). | `myapp` |
| `label` | 화면에 보이는 이름. 업로드 버튼에도 들어갑니다. 패널에서 비워 두고 저장하면 대상 이름과 같게 넣습니다. | `My App (운영)` |
| `test` | 시험용 대상이면 `true`. 자동으로 선택되지 않습니다. | |
| `repo` | **메인 체크아웃**: main 을 받아 두고 빌드하는 작업 폴더. 반영할 파일을 여기서 가져옵니다. | `C:/work/repos/my-app` |
| `mainBranch` | 기본 `main` | |
| `runs` | run 기록 폴더. 운영 파일 백업이 쌓입니다. 저장소 안이면 git 에서 빼 두세요(예: `.local/`). 패널에서 새 대상을 만들 때 비워 두면(가져온 설정도 같음) 저장소 밖인 `~/.prod-deploy/runs/<대상>` 을 씁니다. 이미 있는 대상은 비워 둘 수 없습니다(쌓인 run 의 위치가 모르는 사이 바뀌지 않게). | `C:/work/repos/my-app/.local/deploy` |
| `connection.host` / `port` / `passive` | FTP 주소, 포트(기본 21), 패시브 모드(기본 켬). 주소에는 서버 이름이나 IP 만 넣습니다(계정·포트·경로를 섞지 않음, IPv6 는 지원하지 않음). | `ftp.example.com` |
| `connection.root` | **운영 루트**: FTP 서버에서 압축 푼 WAR 의 맨 위 폴더 | `/webapps/ROOT` |
| `mappings` | **경로 매핑** 목록(아래) | |
| `java` | **Java 빌드 출력**(아래). Java 가 없으면 빼도 됩니다. | |
| `manual` | **손 처리 규칙** 목록(아래) | |
| `checkCommit` | **확인용 커밋**: 이미 운영에 반영된 것이 확실한 커밋. "설정 확인"에 씁니다. | |

`repo`·`runs` 의 `~` 는 홈 폴더로 바뀝니다.

패널에서 `mainBranch`·`port`·`passive`·`runs`·`test` 는 **고급 설정** 안에 있습니다. 접어 둔 채로도 지금 값이 한 줄로 보이고, 운영 대상인지 시험용 대상인지는 맨 위에 늘 보입니다.

## 저장소에서 채우기

대상 설정 탭의 메인 체크아웃 아래 **저장소에서 채우기**는 그 저장소의 폴더 구조를 보고 아래 항목을 제안해 화면의 설정에 넣습니다. 이 PC 의 폴더만 읽고(운영에 접속하지 않음), 저장은 사람이 보고 누릅니다.

| 보는 것 | 넣는 것 |
|---|---|
| `src/main/webapp`(없으면 `WebContent`) | 경로 매핑 `→ /` |
| `build.gradle`·`settings.gradle` / `pom.xml` 과 `src/main/java` | Java 빌드 출력: 소스 `src/main/java`, 결과 `build/classes/java/main`(Gradle) 또는 `target/classes`(Maven), 그 결과 폴더의 경로 매핑 `→ /WEB-INF/classes`, 빌드 명령(안내용) |
| 빌드 결과 폴더의 class 파일(없으면 빌드 파일에 적힌 Java 버전) | class 파일 버전. 둘 다 없으면 Java 8 로 두고 그렇게 알려 줍니다. |
| 소스 폴더 안의 `.java` 가 아닌 파일(쿼리 XML 등, git 이 추적하는 것만) | 경로 매핑 `src/main/java → /WEB-INF/classes`. 넣으면 그 폴더의 `.java` 아닌 파일이 바뀔 때 운영에 올라갑니다. 빌드가 classes 로 옮기지 않는 파일뿐이면 지우세요. |
| `WEB-INF/web.xml`, `META-INF/`, `WEB-INF/lib/`, `src/main/resources/`, `libs/`·`lib/` | 손 처리 규칙(올리지 않고 이유를 보여 줌). 있는 것만 넣습니다. |
| 저장소의 기본 브랜치(이 PC 에 받아 둔 `origin/HEAD`) | main 브랜치 |

- **있는 값은 바꾸지 않습니다.** 빠진 매핑·규칙만 넣고, 비어 있던 빌드 명령만 채웁니다. 설정과 저장소 구조가 다른 점(다른 운영 경로, 다른 Java 버전, 없는 폴더를 가리키는 매핑, 다른 기본 브랜치)은 알려 주기만 합니다.
- **이미 이어져 있는 폴더에는 매핑을 더 넣지 않습니다.** 위 폴더의 매핑이 그 폴더를 다른 운영 경로로 잇고 있으면(예: `build/classes → /custom`) 더 구체적인 매핑을 넣는 순간 반영 위치가 바뀌므로, 넣지 않고 알려 줍니다. Java 빌드 출력을 켤 때 같이 넣는 매핑도 같습니다.
- 저장한 적 없는 **새 대상**에서는 처음 들어 있던 기본값 그대로인 것만 저장소에 맞춥니다: 기본 매핑(`src/main/webapp → /`)의 폴더가 없으면 빼고, main 브랜치가 `main` 그대로면 저장소의 기본 브랜치로 넣습니다. 직접 고친 값은 건드리지 않습니다. 가져온 설정과 쓰고 있는 대상에서는 하지 않습니다.
- 표 아래 칸에 적어 두고 '추가'를 누르지 않은 줄이 있으면 먼저 정리하라고 알려 줍니다(저장할 때도 같습니다).
- Java 버전은 빌드 결과 폴더에서 처음 찾은 class 하나로 읽습니다(링크된 폴더는 따라가지 않음). 빌드 파일에서 읽은 값은 어림이라, 빌드한 뒤 다시 눌러 class 로 확인하세요. 틀린 값으로 저장해도 준비 확인이 class 버전이 다르면 막습니다.
- 저장소 안의 하위 폴더를 메인 체크아웃에 넣었으면 저장소 맨 위 폴더로 바꿉니다(매핑의 로컬 경로가 맨 위 기준이라서).
- 제안은 흔한 Java WAR 구조에 맞춘 것입니다. 운영에서 따로 관리하는 파일, 손으로 등록하는 파일처럼 이 프로젝트에만 있는 손 처리 규칙은 직접 더해야 합니다. 빌드 명령은 이 PC 의 JDK 설정에 맞게 고치세요.

## 경로 매핑

저장소의 폴더 하나를 운영 루트 아래 폴더 하나에 잇습니다. 바뀐 파일이 여러 매핑에 걸리면 **로컬 경로가 가장 긴(가장 구체적인) 매핑**을 씁니다. 매핑은 폴더 단위이고 `*` 같은 패턴은 쓰지 않습니다.

```json
"mappings": [
  { "local": "src/main/webapp",          "remote": "/" },
  { "local": "build/classes/java/main",  "remote": "/WEB-INF/classes" }
]
```

`src/main/webapp/ui/a.xml` → `/webapps/ROOT/ui/a.xml`

## Java 빌드 출력

git diff 에는 `.java` 만 나오므로, 바뀐 `.java` 를 빌드 결과 `.class` 로 바꿔 올립니다(IntelliJ 모듈의 Compiler output 과 같은 개념). 빌드 결과 폴더도 경로 매핑에 있어야 합니다.

```json
"java": { "source": "src/main/java", "output": "build/classes/java/main", "major": 52, "build": ".\\gradlew.bat classes" }
```

- 바뀐 `Foo.java` → `Foo.class` 와 내부 클래스 `Foo$1.class`, `Foo$Inner.class` 를 함께 올립니다.
- `major` 는 class 파일 버전입니다(Java 8 = 52, 11 = 55, 17 = 61, 21 = 65). 다르면 막습니다. 패널에서는 **운영 서버의 Java 버전**으로 고릅니다.
- 패널에서 Java 빌드 출력을 켜면, 빌드 결과 폴더를 `/WEB-INF/classes` 에 잇는 경로 매핑이 없을 때 같이 넣습니다.
- class 가 소스보다 오래됐으면(빌드 안 함) 막습니다. 소스보다 오래된 **내부 클래스**는 지운 클래스의 찌꺼기로 보고 올리지 않습니다.
- `build` 는 안내용입니다. 패널은 빌드하지 않고, 빌드가 필요할 때 이 명령을 보여 줍니다.
- 같은 `.java` 에 함께 선언한 다른 최상위 class(class 의 SourceFile 이 그 파일인 것)도 함께 올립니다.
- **상수 값 대조**: plan 때 운영 class 와 새 class 의 컴파일 시간 상수(`final` 기본형·문자열 필드)를 비교합니다. Java 는 상수를 쓰는 쪽 class 에 값을 복사해 넣으므로, 값이 바뀌거나 상수가 아니게 되면(일반 필드로 바뀜, 없어짐) 쓰는 class 도 다시 올려야 합니다.
  - 쓰는 소스 후보: 상수 이름이 낱말로 나오는 `.java` 전부입니다. Java 는 상수를 여러 길로 부를 수 있어서(`Foo.LIMIT`, `import static`, 상속받아 `LIMIT`, `식.LIMIT`) class 이름으로 거르지 않습니다.
  - 후보가 이 반영 목록에 없으면 **경고**로 그 파일들을 보여 줍니다. 경고는 업로드를 막지 않습니다(IntelliJ 로 올릴 때처럼 판단은 사람이 — [ADR 0005](adr/0005-constant-changes-warn-not-block.md)). 같은 이름의 다른 상수·지역 변수·주석까지 후보가 되므로, 열어 보고 정말 그 상수를 쓰면 그 class 도 함께 올리세요.
  - 후보가 없거나 반영 목록에 다 있으면 **참고**에만 적습니다. 소스에 이름을 `\uXXXX` 로 적은 경우는 찾지 못합니다.
  - 같은 폴더의 class 중 소스 파일 이름(SourceFile)이 없는 것이 있으면 막습니다(어느 소스에서 나왔는지 알 수 없음). 보통의 javac·Gradle 빌드에는 늘 들어 있습니다.
  - `private` 상수는 같은 파일 안에서만 쓰이므로 보지 않습니다. 운영에 없던 새 class 는 비교할 것이 없어 class 형식만 확인합니다.
  - 이미 운영에서 옛 값을 쓰고 있는 class(예전 반영에서 빠진 것)는 찾지 못합니다.
- class 의 나머지 내용은 운영본과 대조하지 않습니다(직전 커밋의 class 가 없음). 업로드 직후 대조는 class 도 합니다.

빌드가 `src/main/java` 아래의 `.java` 가 아닌 파일(메일 템플릿 등)도 `WEB-INF/classes` 로 넣는 프로젝트라면, 그 폴더도 경로 매핑에 넣습니다. `.java` 는 위 규칙이 먼저 처리하고, 나머지 파일은 소스 그대로 올라갑니다.

```json
{ "local": "src/main/java", "remote": "/WEB-INF/classes" }
```

## 손 처리 규칙

패턴에 걸리는 파일은 **올리지 않고** 이유와 함께 보여 줍니다(운영 서버가 다른 파일을 쓰는 설정 파일, jar 교체 등). 위에서부터 처음 맞는 규칙을 씁니다. `**` 는 폴더를 넘어 아무 경로나, `*` 와 `?` 는 폴더 안에서만 맞습니다.

```json
"manual": [
  { "pattern": "src/main/webapp/WEB-INF/web.xml", "reason": "운영 서버가 별도 파일을 씀 — 필요한 변경만 손으로" },
  { "pattern": "src/main/resources/**",          "reason": "환경별 설정 — 손으로" },
  { "pattern": "libs/**",                         "reason": "jar 교체 — 백업·재기동과 함께 손으로" }
]
```

바뀐 파일의 판정 순서: **손 처리 규칙 → 삭제된 파일(늘 손 처리, 운영에서 자동으로 지우지 않음) → 경로 매핑 → 매핑 밖 파일(운영과 상관없음)**.

단 `src/main/` 아래 파일은 빌드가 WAR 에 넣는 곳이라 매핑 밖 파일로 조용히 빠지지 않습니다. 추가·수정은 **문제**로 막습니다(경로 매핑을 추가하거나, 올리지 않을 파일이면 손 처리 규칙에 넣으세요). 삭제는 손 처리 파일로 남깁니다.

## 접속 정보

FTP 사용자·비밀번호는 각자 PC 의 **Windows 자격 증명 관리자**에 `prod-deploy:<대상 이름>` 으로 저장합니다. 패널의 대상 설정 탭 → **접속 정보** 카드에서 넣습니다. CLI 로 넣는 방법은 [cli-and-skill.md](cli-and-skill.md).

예전 bash 도구에서 옮겨 오는 동안에는 대상 설정에 `legacyNetrc`(netrc 파일 경로)를 둘 수 있습니다. 자격 증명 관리자에 정보가 있으면 그것을 쓰고, 없을 때만 netrc 를 씁니다(파일 내용은 읽지 않고 curl 에 경로만 넘김).

새 대상을 만들 때는 접속 정보 카드에 계정을 적어 두면 **설정과 접속 정보 저장** 한 번으로 같이 저장합니다. 설정을 먼저 저장하고 그 이름으로 접속 정보를 저장하며, 접속 정보 저장만 실패하면 설정은 저장된 채로 두고 접속 정보만 다시 저장하게 합니다.

## 접속 확인

접속 정보 카드의 **접속 확인 (운영 읽기)** 는 저장된 설정과 저장된 접속 정보로 FTP 에 로그인해 운영 루트의 목록을 한 번 받아 봅니다. 사람이 누를 때만 접속하고(가져오기·저장만으로는 접속하지 않음), 아무것도 쓰지 않으며, 폴더 내용은 보여 주지 않고 항목 수만 알려 줍니다. FTP 응답은 20초까지만 기다립니다(그 앞에 자격 증명 관리자에서 계정을 읽는 시간이 조금 더 듭니다).

| 결과 | 뜻 |
|---|---|
| 접속됨 | 로그인과 운영 루트 목록 조회 성공. **여기까지만** 확인한 것입니다 — 경로 매핑이 맞는지는 설정 확인으로 봅니다. |
| 접속됨 — 운영 루트 확인 필요 | 로그인은 됐지만 운영 루트가 비어 있음. 운영 루트 경로가 맞는지 보세요. |
| 접속 확인 실패 | 원인을 나눠 알려 줍니다: 서버 이름을 찾지 못함, 서버에 연결하지 못함, 응답 없음, 로그인 실패, 운영 루트 폴더에 들어가지 못함, 목록을 받지 못함, 데이터 연결을 열지 못함(패시브 모드). |

저장하지 않은 설정 변경이 있거나, 접속 정보 칸에 사용자·비밀번호를 적어만 두고 저장하지 않았으면 누를 수 없습니다(저장된 것으로 접속하기 때문). 이때는 앞의 결과도 보여 주지 않습니다. 호스트나 포트를 바꿔 저장한 뒤 누르면 **저장돼 있던 계정으로 새 주소에 로그인**하니, 누르기 전에 카드에 적힌 주소를 확인하세요. 확인용 커밋이 없는 대상은 접속 확인까지 끝나도 "접속까지 확인함"으로만 알려 줍니다(경로 매핑은 확인되지 않음). 그 대상에서 작업(백업·업로드 등)이 도는 중에는 하지 않습니다.

## 설정 확인

대상을 만들거나 매핑을 고친 뒤 **확인용 커밋**을 넣고 대상 설정 탭의 **설정 확인**을 누릅니다. 그 커밋으로 plan 을 돌려(운영 읽기만) 판정합니다.

| 결과 | 뜻 |
|---|---|
| 설정 맞음 | 파일이 "이미 반영됨"으로 나옴. 그 뒤 main 에서 다시 바뀐 파일은 빼고 봅니다. |
| 설정 확인 필요 | 운영에 없는 경로(새 파일)가 나옴 → 매핑·운영 루트가 틀림. 또는 운영에만 있는 수정이 있음. |
| 설정 확인 실패 | 접속·준비 확인에서 멈춤 |

설정 확인으로 만든 run 도 run 기록에 남습니다(막힘). 필요 없으면 run 기록 탭의 **목록 비우기**로 숨기세요.

확인은 **저장된 설정**으로 합니다. 칸을 고친 뒤에는 저장해야 설정 확인을 누를 수 있고, 설정이 바뀌면 앞의 확인 결과는 보여 주지 않습니다.

## 나눠 주기와 가져오기

대상 하나를 팀이 같이 쓸 때는 설정을 글자로 주고받습니다. 팀이 같이 쓰는 것과 PC 마다 다른 것을 나눕니다.

| | 항목 | 내보낸 글자에 |
|---|---|---|
| 팀이 같이 쓰는 것 | 이름, 표시 이름, 시험용 여부, main 브랜치, FTP 주소·포트·패시브·운영 루트, 경로 매핑, Java 소스·결과 폴더·class 버전, 손 처리 규칙, 확인용 커밋, 저장소 주소(`github.com/owner/name` 모양) | 들어감 |
| PC 마다 다른 것 | 메인 체크아웃, run 기록 폴더, FTP 사용자·비밀번호, `legacyNetrc`, `gitRemote`, 빌드 명령(`java.build`) | 들어가지 않음 |

**내보내기** — 대상 설정 탭에서 대상을 고르고 맨 아래 **팀원에게 나눠 주기 → 내보내기**. 나온 글자를 복사해 사내 채널로 보냅니다. 저장하지 않은 변경이 있으면 저장한 뒤에 내보낼 수 있습니다. 받는 쪽에서 거절될 설정(예: FTP 주소에 계정이 섞임, 너무 긴 값)은 내보내지 않고 이유를 알려 줍니다. 비밀번호는 없지만 FTP 주소·운영 루트·저장소 주소가 들어 있으니 밖으로 내보내지 마세요.

저장소 주소는 대상 저장소의 원격(기본 `origin`) 주소에서 만듭니다. 주소 앞의 계정·토큰(`https://user:token@…`)과 프로토콜·`.git` 은 떼고, 호스트는 소문자로, 경로는 적힌 그대로 넣습니다. 기본 포트가 아니면 포트도 남깁니다. **경로 안의 값까지 비밀인지는 도구가 알 수 없으니, 보내기 전에 내보낸 글자의 `remote` 를 읽어 보세요.** 원격이 없거나 `file` 주소·로컬 경로이거나 `?`·`#`·빈칸이 든 주소면 저장소 주소를 넣지 않습니다.

**가져오기** — 대상 설정 탭 **받은 설정 가져오기** 에 글자를 붙여 넣고 **불러오기**. 새 대상으로 열리고, 사람이 **설정 저장**을 누르기 전에는 아무것도 저장되지 않습니다.

- 메인 체크아웃은 **제안**으로 넣습니다. 받은 글자의 저장소 주소로, Orca 에 등록된 작업공간 중 같은 저장소를 받아 둔 폴더를 찾고(main 브랜치인 폴더부터) 그 경로를 넣습니다. 반영에 쓸 폴더가 맞는지 확인하세요. 그 폴더가 main 브랜치가 아니면 알려 주고, 같은 저장소의 다른 폴더가 있으면 함께 보여 줍니다. 찾지 못하면 비워 두니 직접 넣습니다. 같은 저장소인지는 `origin` 의 주소로 봅니다: 포트가 다르거나 경로의 대소문자가 다르면 다른 저장소로 봅니다(github.com·gitlab.com·bitbucket.org 는 대소문자를 가리지 않음). `url.insteadOf` 로 주소를 바꿔 쓰는 저장소, `upstream` 만 같은 fork 는 찾지 못합니다. 저장소 주소가 없는 글자는 지금 보고 있는 작업공간의 저장소를 넣어 봅니다.
- run 기록 폴더는 `~/.prod-deploy/runs/<대상 이름>` 으로 넣습니다(보통 저장소 밖). 여기에는 운영 파일 백업이 쌓이므로, 저장소 안에 두려면 git 에서 빼 둔 폴더여야 합니다. 넣은 위치가 저장소 안이면 알려 줍니다.
- 같은 이름의 대상이 이미 있으면 덮어쓰지 않습니다. 있는 대상을 고쳐 쓰거나, 이름을 바꿔 저장합니다(이름을 바꾸면 run 기록 폴더 끝의 이름도 같이 고칩니다).
- 받은 설정에 확인용 커밋이 없으면 알려 줍니다. 설정 확인을 하려면 이미 운영에 반영된 커밋을 넣고 저장합니다.
- 받은 글자는 엄격하게 검사합니다. 형식 버전이 다르거나, 모르는 항목이 있거나, 저장소·운영 루트 밖으로 나가는 경로(`..`, 절대 경로)나 줄바꿈·탭·보이지 않는 글자가 든 값이 있거나, FTP 주소에 계정·포트·경로가 섞여 있으면 가져오지 않고 이유를 보여 줍니다. 같은 항목이 두 번 적혀 있으면 뒤의 값을 쓰고 그 값을 검사합니다. 대상 설정 파일(`<대상>.json`)을 그대로 붙여 넣은 것도 받지 않습니다(개인 경로가 들어 있음).
- 받은 설정에 빌드 명령은 들어 있지 않습니다. Java 를 반영하려면 **저장소에서 채우기**로 제안을 받거나(비어 있는 빌드 명령만 채웁니다) 보낸 사람에게 물어 넣습니다.
- 가져온 뒤 할 일: 메인 체크아웃 확인 → 접속 정보를 적고 **설정과 접속 정보 저장** → 접속 확인 → 설정 확인. 화면 위쪽의 **다음에 할 일**이 지금 단계를 알려 줍니다.

글자의 모양(형식 `orca-prod-deploy-target`, 버전 1):

```json
{
  "format": "orca-prod-deploy-target",
  "version": 1,
  "id": "myapp",
  "label": "My App (운영)",
  "connection": { "protocol": "ftp", "host": "ftp.example.com", "port": 21, "root": "/webapps/ROOT", "passive": true },
  "mappings": [
    { "local": "src/main/webapp", "remote": "/" },
    { "local": "build/classes/java/main", "remote": "/WEB-INF/classes" }
  ],
  "manual": [{ "pattern": "src/main/webapp/WEB-INF/web.xml", "reason": "운영 서버가 별도 파일을 씀" }],
  "mainBranch": "main",
  "java": { "source": "src/main/java", "output": "build/classes/java/main", "major": 52 },
  "checkCommit": "abc1234",
  "remote": "github.com/owner/my-app"
}
```
